# ADR-0013: WCAG 2.2 Level AA accessibility baseline

- Status: Accepted
- Date: 2026-07-28
- Issue: #61

## Context

ICT Branch Toolkit is intended for public-safety and government users,
including people who use keyboards, screen readers, magnification, touch, and
other assistive technologies. The repository previously targeted WCAG 2.1
Level AA for a limited Phase 1 browser workflow. That did not define a
project-wide standard, generated-content requirements, or repeatable human
evidence.

Automated tools find only some accessibility failures and cannot establish
conformance by themselves. New WCAG 2.2 criteria also affect focus, dragging,
target size, help, redundant entry, and authentication.

## Decision

Adopt WCAG 2.2 Level AA as the required engineering target for complete Toolkit
processes. Apply it to new and changed browser content, responsive states,
maps and structured alternatives, authentication, extensions, and generated
content.

Enforce semantic JSX linting and WCAG-tagged axe checks in CI. Require
human keyboard, resize/reflow, contrast, screen-reader, and generated-content
evidence for release and deployment candidates. Do not describe a passing
automated scan as conformance.

The detailed definition of done, exception process, and evidence requirements
are maintained in
[`docs/governance/accessibility-standard.md`](../governance/accessibility-standard.md).

## Consequences

- Accessibility becomes a release and deployment gate, not a deferred review.
- Every user-facing pull request must declare its accessibility impact.
- New routes and material states must extend the automated browser checkpoints.
- Known barriers remain visible as owned defects and block conformance claims.
- Generated files require format-specific review outside the browser scan.
- Some work requires human assistive-technology testing that CI cannot replace.
